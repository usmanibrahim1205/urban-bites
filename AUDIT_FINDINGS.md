# Urban Bites Phase 6 audit findings

| ID | Severity | Affected area | Root cause and pre-fix reproduction | Correction | Verification |
| --- | --- | --- | --- | --- | --- |
| UB-01 | Critical | Development file access | Vite inherited the repository-wide file allowlist. A non-sensitive fixture under the data directory was returned by the development server with HTTP 200. The live database was never requested through Vite. | Allow only frontend sources and build dependencies. Deny database file types and sensitive paths. Default to loopback, with explicit LAN opt-in. | Verify a disposable fixture is refused and normal assets and the API proxy still work. |
| UB-02 | High | Staff credential rotation | Staff token hashes were independent of the configured password. A session created under one fixture credential remained eligible after starting the application with a different credential. | Bind stored staff session hashes to the configured credential. Keep existing rows intact. An older session requires a fresh sign-in. | Restart a fixture with a different credential and verify the old cookie cannot use staff HTTP or Socket.IO access. |
| UB-03 | Medium | Customer revocation and outage UI | A failed snapshot refresh was ignored while the transport remained connected. The receipt could keep presenting a cached protected bill after a revocation event or brief API failure. | Hide protected session state immediately on revocation or settlement invalidation, fail closed when refresh fails, and reconcile visible clients periodically. Show a connection message while the customer socket reconnects. | Block a refresh after a real browser revocation and check that the protected bill disappears, then check recovery and server-side denial. |
| UB-04 | Medium | Error handling | Unhandled parser errors were logged as whole objects and an unsupported encoding fell through to a generic server error. | Map supported parser error categories to controlled client errors. Log only diagnostic categories for unexpected failures. | Verify bounded request bodies and generic, structured error responses. |
| UB-05 | Medium | Demo preparation | The seed command preserves operational records by design, so it cannot prepare a clean demo using the established table IDs. | Add a command that reads source table IDs and creates a separate SQLite file exclusively. Use the existing menu seed and a fresh identity signer. | Run against a populated fixture, refuse an existing destination, and compare the existing development database before and after the real run. |
| UB-06 | Low | Mobile receipt | Reloading a receipt focused its structural heading and drew an irregular default outline around the title. | Keep programmatic focus for assistive technology and suppress the outline only for the non-interactive receipt heading. | Check that the mobile heading keeps focus without an outline and review the updated screenshot. |

Phase boundaries, cookie separation, request validation, authorization checks, SQL bindings, React rendering, migrations, order and billing transactions, kitchen transitions, QR encoding, print styles, and the existing test suite were reviewed. Physical possession and private-network suitability remain operational checks. The shared credential provides one demo staff role and local HTTP relies on a trusted network. Browser authorization cannot establish continued physical presence or prevent remote submission of unverified requests.
